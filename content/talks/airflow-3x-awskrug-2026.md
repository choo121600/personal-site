## 발표 소개

Airflow를 소개할 때 “ETL에 쓰는 스케줄러”라고 말하면 대체로 이야기가 통합니다. 하지만 설명하고 나면 조금 찜찜합니다. 정해진 시간에 데이터를 옮기는 일만으로는 지금 우리가 만드는 워크플로우를 충분히 설명할 수 없기 때문입니다.

이 발표에서는 Airflow 3.x의 변화를 세 가지 축으로 살펴봅니다. 실행과 오케스트레이션을 분리하는 아키텍처, DAG 작성자가 의존할 수 있는 공개 인터페이스, 그리고 시간뿐 아니라 데이터와 이벤트로 연결되는 워크플로우입니다. 마지막으로 이 변화가 AI 에이전트의 실행을 관측하고 통제하는 데 어떤 의미가 있는지 이야기합니다.

## 발표를 글로 읽기

### 스케줄러라고 설명하면 놓치는 것

익숙한 데이터 파이프라인은 단순한 그림으로 표현할 수 있습니다. 시간이 되면 DAG가 실행되고, Task들이 순서대로 돌아가고, 결과가 데이터 웨어하우스에 적재됩니다.

```text
정해진 시간 → DAG → Task → 데이터 웨어하우스
```

이 그림에서 중요한 것은 언제 실행할지입니다. 그래서 Airflow를 조금 더 똑똑한 Cron으로 이해하는 것도 자연스럽습니다.

하지만 새로운 워크플로우의 끝은 적재가 아니라 행동일 수 있습니다. 이벤트가 들어오면 데이터를 확인하고, 모델이 추론하고, 그 결과에 따라 판단하고 행동합니다. 어떤 단계에서는 사람의 승인을 기다려야 합니다.

```text
이벤트 → 데이터 → 모델 → 추론 → 판단 → 행동
```

Airflow 3.x를 볼 때 중요한 질문은 “어떤 기능이 추가됐는가?”만이 아닙니다. **Airflow가 감당하려는 워크플로우의 범위가 어떻게 넓어졌는가?**를 함께 봐야 합니다.

### 실행하는 일과 조율하는 일을 나누기

Airflow 2.x에서는 Task가 실행 중 메타데이터 DB에 직접 접근하는 구조가 익숙했습니다. Connection, Variable, XCom과 상태 정보가 이 경계에 걸쳐 있었습니다.

3.x에서는 Task Execution API가 실행과 Airflow 코어 사이의 접점이 됩니다. Task는 DB에 직접 접근하는 대신 API를 통해 Airflow와 소통합니다. Supervisor와 Task SDK는 이 실행 경계를 구성하는 역할을 맡습니다. DAG 파싱도 독립된 DAG Processor가 담당합니다.

여기서 구분하고 싶은 것은 두 가지입니다.

- **오케스트레이션:** 무엇을 언제 어떤 순서로 실행하고, 실패하면 어떻게 처리할지 결정하는 일
- **실행:** 실제 사용자 코드가 특정 환경에서 돌아가는 일

둘을 분리하면 실행 환경을 선택하는 문제와 워크플로우를 조율하는 문제를 따로 다룰 수 있습니다. 워커를 격리하거나 원격 환경으로 확장할 때도, 모든 실행 환경에 메타데이터 DB 접근을 열어주는 방식에서 벗어날 수 있습니다.

### Dag 작성자에게 필요한 것은 안정적인 약속

운영하는 사람과 Dag를 작성하는 사람이 항상 같은 팀인 것은 아닙니다. 코어의 내부 구조가 바뀔 때마다 모든 DAG가 그 변화를 따라가야 한다면, 플랫폼 업그레이드가 사용자 코드 전체의 수정 작업이 됩니다.

`airflow.sdk`가 중요한 이유가 여기에 있습니다. Dag 작성자가 의존할 공개 인터페이스를 정하고, 내부 구현과 사용자 코드 사이에 경계를 만듭니다.

이것이 모든 업그레이드에서 수정이 필요 없다는 뜻은 아닙니다. 다만 내부 구현을 직접 참조하는 대신, 어떤 인터페이스를 기준으로 코드를 작성해야 하는지 명확해집니다. 운영팀, Dag 작성자, Provider 개발자가 함께 의존할 계약이 생기는 것입니다.

### 시간이 아니라 데이터가 준비됐을 때

앞 단계가 끝날 것으로 예상되는 시간에 다음 DAG를 예약해 두는 방식은 흔합니다. 하지만 실행 시간이 길어지면 데이터가 준비되기 전에 다음 작업이 시작될 수 있고, 반대로 데이터가 일찍 도착해도 정해진 시간까지 기다려야 합니다.

Asset 기반 스케줄링은 이 연결을 데이터 상태로 표현합니다. 한 Task가 Asset을 갱신하면 그 Asset을 소비하는 DAG를 실행하는 식입니다. 발표에서는 Task가 성공했을 때 갱신된다는 점도 짚었습니다. 실패하거나 스킵된 작업을 데이터가 준비됐다는 신호로 취급해서는 안 되기 때문입니다.

개별 DAG를 따로 보는 대신, 데이터가 어떤 작업을 깨우고 그 작업이 다시 어떤 데이터를 만드는지 하나의 큰 흐름으로 볼 수 있습니다.

```text
이벤트 → Asset A → 워크플로우 A → Asset B → 워크플로우 B
```

### 워크플로우에도 버전이 필요하다

“지난주에는 됐는데 오늘은 안 됩니다”라는 문제를 조사할 때, 지금 저장소의 코드만으로는 충분하지 않을 수 있습니다. 지난주 실행에 사용한 코드가 무엇이었는지도 알아야 합니다.

DAG Bundle은 워크플로우를 버전이 있는 산출물로 다루는 방향입니다. 실행 이력과 코드의 버전을 함께 추적할 수 있어야 과거 실행을 이해하고 문제를 재현하기가 쉬워집니다.

시간 대신 데이터 상태로 작업을 연결하는 것과, 실행 당시의 코드를 추적하는 것은 별개의 기능처럼 보입니다. 하지만 둘 다 워크플로우를 단순한 시간표보다 더 명시적으로 다루려는 변화입니다.

### 에이전트의 답보다 실행 과정을 남기기

AI 에이전트가 답을 만들었다고 해서 작업이 끝나는 것은 아닙니다. 어떤 도구를 호출했는지, 어느 단계가 실패했는지, 무엇을 다시 실행해야 하는지 설명할 수 있어야 합니다.

LLM 호출과 도구 사용을 이름 있는 Task로 나누면 각 단계에 로그와 결과, 재시도 이력이 남습니다. 병렬 작업은 Dynamic Task Mapping으로 펼칠 수 있고, 사람의 판단이 필요한 지점에는 HITL을 둘 수 있습니다.

여기서 HITL은 단순히 결과를 사람이 나중에 읽는다는 뜻이 아닙니다. 승인·선택·입력이 워크플로우의 한 단계가 되어 다음 실행 흐름을 결정하는 것입니다.

모든 에이전트가 관측 불가능하다는 뜻도 아닙니다. 중요한 것은 **우리의 실행 구조에서 어떤 기록과 제어 지점을 명시적으로 남길 것인가**입니다. Airflow의 Task 단위 실행 모델은 그 질문에 답하는 한 가지 방법입니다.

## 정리

1. **실행과 오케스트레이션을 분리합니다.** 어디서 코드를 실행할지와 무엇을 언제 실행할지를 따로 설계할 수 있습니다.
2. **작성 인터페이스와 실행 버전을 명확하게 만듭니다.** 사용자 코드가 의존할 계약과 과거 실행을 추적할 근거가 필요합니다.
3. **시간만이 유일한 시작 조건은 아닙니다.** 데이터의 변화와 이벤트, 사람의 판단도 워크플로우의 일부가 됩니다.

Airflow 3.x는 Dag 스케줄러의 업그레이드이기도 하지만, 더 넓게는 워크플로우 오케스트레이터가 다룰 수 있는 범위를 확장하는 변화입니다.
